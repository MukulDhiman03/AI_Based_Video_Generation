# Authentication QA — 17 October 2026

Verdict: **fails the supplied invite-only registration requirement**. The remaining tested authentication flows pass. No application code was changed.

Environment: local application at `http://127.0.0.1:3005`, configured MongoDB database `vidsutra_ai`, ChatGPT in-app browser at its current 727 × 827 viewport. Build and TypeScript checked from the current checkout; browser/API checks ran against the existing local development server.

## Findings

### P1 — Registration is open despite the invite-only brief

Reproduce: POST `/api/auth/sign-up/email` with a unique valid email, name, and a 12–128-character password, omitting `x-vidsutra-invite` or supplying an empty value.

Expected under the supplied brief: reject registration, with no user/account/session created.

Actual: HTTP 200, persisted user and hashed password, active session, and subsequent login succeeds. Confirmed for both missing and blank headers by `npm run test:auth`; additional password-boundary checks also registered accounts without invitations. The browser advertises “Everyone is welcome. An invitation code is optional.”

Cause: `src/lib/server/auth.ts:47` returns early when the token is absent. The database create hook also validates invitations only when a token exists. README and the current integration tests explicitly describe/assert open registration, so a green suite does not establish the invite-only requirement.

Recommendation: reconcile the requirement before release. If invite-only is intended, require a valid email-bound invitation on the server and change the missing/blank invitation tests to expect rejection and no persisted records. Align UI and README with that behavior.

### P3 — Auth form flashes before session restoration

Reproduce: complete signup, then reload the signup page while signed in.

Actual: the signup form briefly appears before being replaced by the signed-in confirmation. Session persistence ultimately succeeds.

Cause: `AuthForm` reads session data without rendering a pending state while `useSession()` resolves (`src/components/auth/auth-form.tsx`).

Recommendation: render a neutral loading state until the initial session lookup finishes.

## Limits and cleanup

Email delivery, recovery email/reset completion, and verification email completion were not tested because delivery is not configured. These remain incomplete features, as disclosed in the brief. No real recipient was emailed.

This was a single-browser functional QA pass. Full mobile/device, cross-browser, accessibility, load, outage, and production HTTPS cookie testing were not performed. Successful build does not imply the live development server was running that production build.

The integration suite and additional API checks cleaned their synthetic records. The separately created browser fixture's user, account, sessions, invitation and temporary credentials file were removed. Application source and existing user data were not changed. Browser requests may leave ordinary shared rate-limit counters, which were not broadly deleted.
